# 감상 기록 수집 및 개인화 추천 명세서

- **Date**: 2026-11-20
- **Version**: v1.1.0
- **관련 코드**: `apps/api/src/listening/`, `apps/web/src/utils/listeningTelemetry.js`, `apps/web/src/components/home/ForYouSection.jsx`
- **관련 스키마**: [supabase_listening_events.sql](./supabase_listening_events.sql), [supabase_playlist_signals.sql](./supabase_playlist_signals.sql)

사용자의 감상 기록을 쌓아 두고, 그 기록으로 홈 화면 **취향 저격 추천**(노래·플레이리스트)을 만드는 기능의 명세입니다. 쌓인 기록은 나중에 시간대별·연령별 통계와 추천 고도화에도 씁니다.

---

## 1. 감상 기록 수집

### 1.1. 재생 세션

곡 하나를 재생하는 동안을 재생 세션 하나로 보고, 끝날 때 `play_events`에 한 줄을 남깁니다.

- **시작**: `playTrack` 호출 시. 곡 선택 없이 재생만 다시 시작된 경우(새로고침 후 이어 듣기)는 플레이어 폴링에서 시작합니다.
- **끝**: 곡 종료(`ended`), 다른 곡으로 전환(`switched`), 탭 닫기(`closed`), 재생 실패(`error`)
- **실제 재생 시간**: 200ms 폴링에서 재생 중인 시간만 더합니다. 일시정지·탐색 시간은 빼고, 2초 넘게 비면 버립니다.
- **전송**: `POST /api/events/play` (`fetch keepalive`). 1초 미만은 보내지 않습니다.
- **기존 30초 유효 재생 로그**(`POST /api/chart/play-log`)는 실시간 인기 순위용으로 그대로 따로 보냅니다.

### 1.2. 기록 항목 (`play_events`)

| 항목 | 설명 |
| :--- | :--- |
| `user_id` / `client_id` / `session_id` | 로그인 사용자(서버가 토큰 검증), 브라우저 식별자, 탭 식별자 |
| `track_key`, `title`, `artist`, `video_id` | 곡 식별. `track_key`는 차트와 같은 "곡명_아티스트" 소문자 규칙 |
| `listened_sec`, `duration_sec`, `completion` | 실제 재생 시간, 곡 길이, 완주율 |
| `end_reason`, `is_skip`, `seek_count` | 끝난 이유, 스킵 여부(직접 넘김 + 30초 미만 + 절반 미만), 구간 이동 횟수 |
| `source_type`, `source_id` | 재생한 목록: `my`, `shared`, `curated`, `chart`, `queue`, `recommend`, `search`, `unknown` |
| `trigger` | 재생을 시작한 방식 (아래 표) |
| `rec_algo`, `rec_request_id` | 추천에서 시작한 경우 알고리즘 버전과 추천 응답 ID |
| `tz`, `local_hour`, `local_dow`, `device`, `locale` | 사용자 기기 기준 시간대·시각·요일, 기기 종류, 언어 |

### 1.3. 재생 시작 방식 (`trigger`)

| 값 | 의미 | 기록 위치 |
| :--- | :--- | :--- |
| `search` | 검색 결과에서 골라 재생 | `SearchTrackRow`, `SearchTopResult`, `SearchPanel` 전체·셔플 재생 |
| `click` | 목록·카드에서 직접 눌러 재생 (기본값) | 그 밖의 모든 `playTrack` 호출 |
| `skip_button` | 플레이어 다음/이전 버튼 | `AudioContext`가 노출하는 `playNext`·`playPrevious` |
| `auto` | 앞 곡 종료·한 곡 반복·재생 실패로 자동 전환 | `handleTrackEnded`, 플레이어 오류 처리 |
| `resume` | 곡 선택 없이 재생만 다시 시작 | 플레이어 폴링 |

검색에서 시작한 목록에서 이어지는 `auto`·`skip_button` 재생도 출처는 `search`로 남깁니다.

### 1.4. 추천 노출·클릭 (`recommendation_events`)

- 추천 탭이 화면에 실제로 보였을 때 탭별로 한 번 `impression`, 카드를 누르면 `click`을 보냅니다.
- 알고리즘 버전(`algo`)과 응답 ID(`request_id`)를 함께 남겨, 버전별 클릭률 비교와 노출 → 클릭 → 감상 연결 분석에 씁니다.

### 1.5. 보관 및 삭제

- 두 테이블 모두 **2년**이 지난 기록은 pg_cron 작업(`sofar-purge-listening-events`)이 매일 삭제합니다.
- 회원 탈퇴 시 `account.service`가 해당 사용자의 기록을 바로 삭제합니다.
- 쓰기는 API 서버(service_role)만 합니다. 사용자는 RLS로 본인 감상 기록만 조회할 수 있습니다.
- 개인정보 처리방침(`apps/web/src/pages/LegalPage.jsx`)의 수집 항목·보관 기간과 반드시 맞춰야 합니다.

## 2. 추천 알고리즘 (`hybrid-v1`)

점수 계산은 외부 의존성 없는 순수 함수 `apps/api/src/listening/recommend.engine.ts`에 있습니다. 알고리즘을 바꿀 때는 이 파일과 `ALGO_VERSION`을 바꿉니다.

### 2.1. 취향 프로필

곡마다 `취향 점수 = 최근성 감쇠 × 재생 반응 × 시작 방식 무게`를 더합니다.

- **최근성 감쇠**: 반감기 21일
- **재생 반응**
  - 10초 미만 0, 30초 이상 최소 0.5, 완주율만큼 최대 1.0, 끝까지 들으면 +0.2
  - 직접 넘김(스킵)은 −0.3, 자동으로 나온 곡을 넘기면 −0.15
  - 탭 닫기·재생 오류는 감점하지 않음
  - 감점은 그 곡에만 주고 아티스트에는 주지 않음
- **시작 방식 무게**: `search` 1.3, `click`·`resume` 1.0, `skip_button` 0.8, `auto` 0.5 (예전 기록은 1.0)
- **감상 외 신호**: 즐겨찾기 1.2, 내 플레이리스트에 담은 곡 0.5
- 같은 곡 판단은 괄호 표기와 공동 아티스트를 무시하고(`songIdentityOf`), 아티스트는 주 아티스트만 봅니다(`Ke$ha` = `Kesha`).

### 2.2. 후보와 점수

| 신호 | 가중치 | 데이터 |
| :--- | :--- | :--- |
| 함께 담김 | 0.35 | 좋아한 곡이 들어 있는 sofar·공유 플레이리스트의 다른 곡 |
| 비슷한 곡 | 0.35 | 취향 상위 5곡의 Last.fm `track.getSimilar` (곡별 24시간 캐시) |
| 아티스트 취향 | 0.30 | 아티스트별 취향 점수 |
| 인기도 | 0.15 | sofar 실시간 인기 순위·뜨고 있는 음악 순위 |

### 2.3. 고르기

- 이미 아는 곡(들은 적 있거나 즐겨찾기·내 플레이리스트에 있는 곡)과 넘긴 곡은 제외하고, 같은 아티스트는 2곡까지만 넣습니다.
- 개인화 자리 = 전체 × min(0.85, 0.4 + 취향 총량 × 0.2). 나머지는 인기곡으로 채웁니다.
- 취향 총량이 0.3 미만이면 기록이 없는 사용자로 보고 인기 위주로 보여 줍니다(제목: "이런 음악은 어때요?").
- 플레이리스트는 관련도 75% + 인기 25%로 고르고, 본인 플레이리스트는 빼며, 새로 공유된 플레이리스트를 최대 2자리 섞습니다.
- 같은 날·같은 사용자는 같은 순서가 나오도록 하루 단위 시드로 미세하게 섞습니다.
- 결과: 노래 24개, 플레이리스트 최대 12개. 카드마다 추천 이유를 붙입니다(예: "Kesha 노래를 즐겨 들어서", "'TiK ToK'과 비슷한 곡").

### 2.4. 갱신

- 서버는 사용자별 결과를 5분 캐시하고, 새 감상 기록이 들어오면 그 사용자의 캐시를 지웁니다.
- 웹은 홈에 들어올 때마다 다시 요청합니다. 홈을 보는 동안에는 다시 받지 않아 목록이 갑자기 바뀌지 않습니다.

## 3. API

| 메서드 | 경로 | 설명 |
| :--- | :--- | :--- |
| `POST` | `/api/events/play` | 재생 세션 기록. `Authorization` 헤더가 있으면 검증된 사용자로 기록 |
| `POST` | `/api/events/recommendation` | 추천 노출·클릭 기록 |
| `GET` | `/api/recommend/home?clientId=` | 홈 추천. 로그인 시 `Authorization` 헤더 |

`trigger` 컬럼이 아직 없는 DB에서도 기록이 끊기지 않도록, API는 컬럼이 있는지 먼저 확인하고 없으면 그 값만 빼고 저장합니다.

## 4. 화면

- **위치**: 홈 하단, `sofar 플레이리스트`·`실시간 인기 순위` 아래 (`ForYouSection`)
- **탭**: 노래 / 플레이리스트
- **노래 카드**: 둥근 커버, 앨범 이미지가 없으면 LP판(`VinylFallback`, 곡마다 같은 톤의 다른 배경색), 재생 중이면 LP판이 돌고 테두리가 강조색으로 바뀜
- **플레이리스트 카드**: 겹친 카드 모양, 곡 수 표시, "플레이리스트 · 만든 사람" + 아바타(sofar 로고 또는 직접 올린 프로필 이미지, 익명이면 기본 아바타)

## 5. 플레이리스트 반응과 '관심 없음' (학습 재료)

스스로 정확해지는 추천(밴딧 → 가중치 학습 → 협업 필터링)의 1단계로, 결과를 판단할 신호를 늘리고 어뷰징을 막습니다.

### 5.1. 신호

| 신호 | 누가 | 저장 | 중복 차단 |
| :--- | :--- | :--- | :--- |
| 좋아요 | 회원 | `playlist_likes` | 계정·플레이리스트당 1개 |
| 조회 | 회원·비회원 | `playlist_views` | 사람(회원 또는 브라우저)당 하루 1회 |
| 공유 유입 | 링크로 들어온 다른 사람 | `playlist_shares`, `playlist_share_visits` | 공유 링크당 사람 1회, 공유한 본인 제외 |
| 관심 없음 | 회원·비회원 (본인 추천에만 영향) | `recommendation_feedback` | 사람·항목당 1개 |

- 공유 링크는 복사할 때마다 무작위 코드(`/p/{id}?s={code}`)를 붙여, 버튼 클릭 수가 아니라 **실제로 들어온 사람 수**를 셉니다.
- 사이드바에서 다른 사람의 공유 플레이리스트를 열면 머리글에 좋아요 버튼이 나오고, 조회가 기록됩니다.
- 취향 저격 추천 카드의 더보기 메뉴에 '관심 없음'이 있습니다. 누르면 바로 사라지고, 서버 저장이 실패하면 다시 나타납니다.

### 5.2. 어뷰징 방지
- 좋아요는 서버가 토큰을 검증한 회원만. 본인 플레이리스트와 비공개 플레이리스트에는 반응·조회를 받지 않습니다.
- 요청 수 제한: IP당 1분 300회, 계정·브라우저당 쓰기 1분 30회.
- 순위에는 원본 횟수가 아니라 `get_playlist_signal_stats` 함수의 **사람 수**만 씁니다. 좋아요는 가입 3일 이상 계정만 셉니다.
- 저장이 실패하면 성공처럼 보이지 않게 오류를 돌려줍니다.

### 5.3. 추천 반영
- **관심 없음**: 그 곡·플레이리스트를 빼고, 곡의 아티스트 취향 점수를 0.4 깎습니다.
- **사회적 점수**: `log(1 + 3×좋아요 + 2×최근 14일 좋아요 + 2×감상자(30일) + 2×공유 유입(30일) + 0.5×조회자(30일))`를 최댓값으로 나눈 값.
  - 개인화: 관련도 0.6 + 인기 0.2 + 사회적 점수 0.2
  - 기록 없는 사용자: 인기 0.5 + 사회적 점수 0.5
- '새로 공유된 플레이리스트' 자리는 최근 14일 좋아요가 많은 순서가 먼저입니다(이유: "요즘 좋아요를 받는 플레이리스트").
- 응원(hype)도 검토했지만 좋아요와 역할이 겹쳐 사용자에게 헷갈릴 수 있어 넣지 않았습니다.

## 6. 향후 고도화

- 감상 기록이 수만 건 이상 쌓이면 협업 필터링(행렬 분해·임베딩) 후보를 추가하고, `recommendation_events`로 `hybrid-v1`과 A/B 비교합니다.
- 연령·성별 통계: `profiles.birth_year`, `profiles.gender` 컬럼은 준비되어 있으나, 입력 화면과 개인정보 처리방침 갱신 전에는 수집하지 않습니다.
